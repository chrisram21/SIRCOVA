# SPEC 29 — Node.js 24 y cuerpos comprimidos (hotfix de seguridad)

> **Estado:** Aprobado
> **Historia:** ninguna. Es un hotfix de mantenimiento y seguridad del sprint 3 (excepción a la regla de una HU por spec de `CLAUDE.md`).
> **Depende de:** SPEC 27, SPEC 28
> **Fecha:** 2026-10-29
> **Objetivo:** Pasar el proyecto a Node.js 24.22.1 o posterior y hacer que el backend rechace los cuerpos comprimidos (415) y los demasiado grandes (413) en lugar de descomprimirlos o responder 500.

## Por qué existe este spec

El 21 de octubre de 2026, Node.js publicó una actualización de seguridad para las líneas 22, 24 y 26, con 10 CVE corregidas. La más grave es la **CVE-2026-111497**:

- Es una escritura fuera de límites en el **descompresor Brotli** de Node, que permite ejecutar código en el servidor.
- CISA la agregó el 27 de octubre a su lista de fallas que ya se están explotando.
- Otras de las CVE permiten saltarse la validación del certificado TLS. El backend se conecta por TLS a Aiven y a Atlas.

**SIRCOVA está expuesto de forma directa:**

- Express 5 usa `body-parser` 2, y `express.json()` descomprime solo los cuerpos con `Content-Encoding: br`, `gzip` o `deflate`.
- Cualquier persona, sin cuenta, puede mandar a `POST /api/v1/auth/login` un cuerpo Brotli preparado y hacer que Node lo descomprima.

Hoy el equipo usa Node v22.23.2 y npm 10.9.8.

La base del spec es `docs/SPECS/PROPUESTA_NODE_24.md` (decisiones del equipo del 2026-10-29). En la fase de preguntas se cerraron tres puntos que la propuesta dejaba abiertos:

- Las pruebas del cuerpo usan un login **sin `contrasena`**, que responde 400 sin tocar la base, para no dejar filas `LOGIN_FALLIDO` en la bitácora.
- La lista de códigos HTTP de `AGENTS.md` y de `INSTRUCCIONES_BACKEND.md` suma el 413, el 415 y el 423 (este último ya existía y no estaba anotado).
- Luis instala Node 24 a mano y el agente comprueba la instalación.

**Diferencias con la propuesta:** la propuesta dice que el 413 y el 415 «se suman a los de la lista de `AGENTS.md`, como ya pasó con el 423». El 423 nunca se agregó a esa lista; este spec lo agrega junto con los otros dos.

## Modelo de datos

Este spec no cambia la base de datos ni las estructuras del frontend.

### Versión de Node en el repositorio

```text
# .nvmrc (raíz)
24
```

```json
// backend/package.json y frontend/package.json, campo nuevo
"engines": { "node": ">=24.22.1" }
```

- `engines` no bloquea la instalación. Con Node 22, `npm ci` muestra el aviso `EBADENGINE` y sigue.
- Los `package-lock.json` **no reciben** `engines`: agregarlo exige regenerarlos con `npm install`.

### Lectura del cuerpo (`app.js`)

```js
app.use(express.json({ inflate: false, limit: '1mb' }));
```

- `inflate: false`: `body-parser` rechaza todo cuerpo con `Content-Encoding` distinto de `identity`, con `err.type === 'encoding.unsupported'` y estado 415. Ya no descomprime nada.
- `limit: '1mb'` (antes 100 KB, el valor por defecto): un cuerpo más grande da `err.type === 'entity.too.large'` y estado 413, sin leerlo completo.

**Por qué 1 MB.** El cuerpo más grande de la API es el `PUT /reportes/{id}/vacunas/{vacunaId}` de la captura:

- Cada celda con valor pesa unos 110 a 130 bytes, así que 100 KB alcanzan para unas 800 celdas.
- Una vacuna con 4 dosis, 2 sexos y 3 grupos de edad tiene 24 celdas por municipio. Un establecimiento que reciba personas de los 29 municipios restantes del departamento, además del suyo, se acerca a ese número.
- Con 1 MB queda margen de sobra y sigue cortando un cuerpo absurdo.

### Errores nuevos (`manejarErrores`)

| `err.type` | Estado | `codigo` | `mensaje` |
|---|---|---|---|
| `encoding.unsupported` | 415 | `CODIFICACION_NO_ADMITIDA` | El servidor no acepta cuerpos comprimidos. |
| `entity.too.large` | 413 | `CUERPO_DEMASIADO_GRANDE` | El cuerpo de la solicitud es demasiado grande. |

- Van con el formato común `{ "error": { "codigo", "mensaje" } }`, igual que el `entity.parse.failed` que ya existe.
- No se escriben en la consola: son errores del cliente, no del servidor. Hoy los dos salen como 500 `ERROR_INTERNO` con `console.error`.
- No van a la bitácora: la petición se corta antes de llegar a la ruta, como el 400 de un JSON mal formado.

### Contrato (`openapi.yaml`)

- `components.responses.CodificacionNoAdmitida` (415) y `components.responses.CuerpoDemasiadoGrande` (413), con el esquema de error común y un ejemplo cada una.
- Un párrafo **Cuerpo de la solicitud** en `info.description`: ningún endpoint acepta `Content-Encoding` (salvo `identity`) y el cuerpo no puede pasar de 1 MB. Nombra las dos respuestas.
- No se agregan a cada operación: el párrafo general las cubre.

## Pruebas

`backend/tests/cuerpoDeLaSolicitud.test.js`, con `supertest` contra `POST /api/v1/auth/login`:

- Ningún caso lleva `contrasena`. Así, los que pasan la lectura del cuerpo responden 400 `ENTRADA_INVALIDA` antes de tocar la base, y la prueba no inicia sesión ni deja filas en la bitácora.
- Los cuerpos comprimidos se mandan como `Buffer` con `Content-Type: application/json` y su `Content-Encoding`.

| Caso | Cuerpo | Espera |
|---|---|---|
| Brotli | `{ nombreUsuario }` comprimido con `zlib.brotliCompressSync`, `Content-Encoding: br` | 415 `CODIFICACION_NO_ADMITIDA` |
| gzip | El mismo, con `zlib.gzipSync` y `Content-Encoding: gzip` | 415 `CODIFICACION_NO_ADMITIDA` |
| Más de 1 MB | `{ nombreUsuario, relleno }` con un relleno de más de 1 MB | 413 `CUERPO_DEMASIADO_GRANDE` |
| Unos 200 KB | `{ nombreUsuario, relleno }` con un relleno de unos 200 KB (más que el límite anterior) | 400 `ENTRADA_INVALIDA` |
| Normal | `{ nombreUsuario }` sin comprimir | 400 `ENTRADA_INVALIDA` |

**Agregado al implementar:**

- Los casos comprimidos mandan el `Buffer` con `.serialize((bytes) => bytes)`. Sin eso, supertest lo convierte a JSON y el cuerpo no llega comprimido.
- Los casos del 415 y del 413 espían `console.error` y comprueban que no se llama.
- Contra el `app.js` y el `errores.js` anteriores, Brotli y gzip responden 400 (el cuerpo se descomprimía y llegaba al login), y los casos de más de 1 MB y de 200 KB responden 500.

## Decisiones

- **Sí:** Node.js 24 LTS, 24.22.1 o posterior (decisión del equipo). **No:** el parche 22.23.4: la línea 22 deja de recibir parches en abril de 2027 y la 24 los recibe hasta abril de 2028. La 22.23.4 queda como plan B.
- **Sí:** el instalador de Windows de nodejs.org, que reemplaza a la 22 (decisión del equipo). **No:** nvm u otro gestor de versiones, que suma una herramienta que el equipo no usa.
- **Sí:** `.nvmrc` con `24` y `engines` con `>=24.22.1` (decisión del equipo). `.nvmrc` dice la línea; `engines` avisa con `EBADENGINE` a quien siga con una versión vulnerable. **No:** `engine-strict`, que bloquearía la instalación a un integrante a mitad de su trabajo.
- **Sí:** solo `npm ci`, y los `package-lock.json` no se tocan (decisión del equipo). **No:** `npm install` con npm 11, que agrega líneas al lock del frontend (`oxide-wasm32-wasi`) y el `engines`, y ensucia el diff de un hotfix.
- **Sí:** `inflate: false` (decisión del equipo; el SPEC 27 lo dejó para este hotfix). El frontend nunca manda cuerpos comprimidos, y una falla futura en un descompresor o una bomba de descompresión ya no llega a Node. **No:** confiar solo en el parche de Node.
- **Sí:** el límite sube a 1 MB (decisión del equipo). **No:** dejar los 100 KB, que ya quedan justos para una captura con los 30 municipios del departamento.
- **Sí:** 413 y 415 con el formato común y sin `console.error` (decisión del equipo). **No:** dejarlos como 500 `ERROR_INTERNO`, que culpa al servidor de un error del cliente y llena la consola.
- **Sí:** las respuestas comunes y un párrafo en la descripción general del contrato. **No:** agregarlas a cada operación del contrato, que repetiría lo mismo en todos los endpoints con cuerpo.
- **Sí:** las pruebas usan un login sin `contrasena`, que responde 400 antes de tocar la base (decidido en la fase de preguntas). **No:** credenciales falsas, que dejarían en cada corrida filas `LOGIN_FALLIDO` que no se pueden borrar.
- **Sí:** `AGENTS.md` §4 e `INSTRUCCIONES_BACKEND.md` listan el 413, el 415 y el 423 (decidido en la fase de preguntas). **No:** dejar los códigos solo en el contrato.
- **Sí:** Luis instala Node y el agente comprueba (decidido en la fase de preguntas). El agente no puede ejecutar el instalador.
- **Sí:** no se corre una línea base con Node 22 (decisión del equipo). Las dos suites pasaron completas el 2026-10-29.
- **Sí:** `npm audit` solo como informe. **No:** corregirlo aquí, porque cambiaría dependencias y lock.
- **Sí:** los specs viejos siguen diciendo «Node.js 22». Son el registro de cuándo se escribieron.

## Plan B: volver a Node 22.23.4

Se vuelve si con Node 24 **el sistema deja de funcionar de cualquier forma**. Por ejemplo:

- `npm ci` no instala alguna dependencia;
- falla una prueba que en Node 22 pasa;
- falla la conexión TLS con Aiven o con Atlas;
- la API no arranca, Vite no arranca o `vite build` falla;
- algo de la prueba manual no funciona.

**No cuentan como falla:**

- los timeouts sueltos de Aiven en la suite del backend: se repite solo ese archivo;
- los timeouts de las pantallas `lazy` en la suite del frontend: se repiten solas o con `--maxWorkers=2`;
- un `ENOTFOUND` de Aiven: es la base apagada del plan gratuito, no Node;
- los avisos `DeprecationWarning` y `ExperimentalWarning`: se anotan.

**Cómo se vuelve:**

1. Luis instala el MSI de la **22.23.4** encima.
2. `npm ci` en los dos proyectos.
3. `.nvmrc` pasa a `22` y `engines` a `>=22.23.4 <23`.
4. Los documentos dicen «Node.js 22 LTS» (sin la nota del sprint 3 en `CONTEXTO PROYECTO SIRCOVA.md`).

`inflate: false`, el límite de 1 MB, el 413 y el 415 se mantienen igual.

## Riesgos

| Riesgo | Mitigación |
|---|---|
| Un integrante no actualiza y sigue con Node 22 vulnerable | El aviso `EBADENGINE` de `engines` y los pasos para el equipo en el PR |
| `npm install` con npm 11 ensucia los lock | Este spec usa solo `npm ci`; la nota de `CLAUDE.md` explica las líneas que aparecerán más adelante |
| La terminal de VS Code sigue usando el Node viejo | Cerrar y volver a abrir VS Code después de instalar (paso 1) |
| Un `node` de la versión anterior queda ocupando el puerto | Revisarlo antes de arrancar la API o Vite (paso 1) |
| El OpenSSL de Node 24 rechaza el certificado de Aiven o de Atlas | La suite completa y el arranque de la API lo detectan; si pasa, plan B |
| Una falla que ya existía se atribuye a Node 24 | La línea base del 2026-10-29: las dos suites pasaban completas con Node 22 |
| Aiven apagado se confunde con una falla de Node | Un `ENOTFOUND` es Aiven: se pide encenderlo y se repite |
| Un cliente futuro necesita mandar más de 1 MB | Hoy ningún cuerpo se acerca; si llega a pasar, se sube el límite en su propio spec |

## Lo que **no** entra en este spec

- Cambiar dependencias o sus versiones, y regenerar los `package-lock.json`.
- Corregir lo que reporte `npm audit`.
- Docker, CI o despliegue.
- Pasar a Node 26.
- Cambiar los specs anteriores que dicen «Node.js 22».
- La vista previa obligatoria antes de publicar un esquema.

Cada uno, si se hace, va en su propio spec.
